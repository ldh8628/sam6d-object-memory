# 검증 기록 — 2026-09-08

실행기와 네이티브 노드를 빌드하고, 카메라 없이 실제 ORB-SLAM3·RealSense SDK 재생·독립 ROS 수신 프로세스로 검증했다. **물리 카메라와 반대 노트북 LAN 수신은 검증하지 않았다.** 사용자가 제거한 카메라를 요구하거나 SSH·네트워크 주소를 변경하지 않았다.

## 환경과 데이터

- Intel Core Ultra 7 258V, WSL Ubuntu-22.04, 기존 ROS 2 Jazzy/Fast DDS, OpenCV 4.5.4, librealsense 2.56.4. Release 빌드, 현재 CPU용 명령어 집합 사용.
- [TUM RGB-D 공식 데이터](https://cvg.cit.tum.de/data/datasets/rgbd-dataset): `fr1/xyz`로 시험 Atlas를 생성하고 `fr1/rpy`의 회전을 평가했다. 이 Atlas는 사용자의 실제 운용 지도가 아니다.
- `xyz`: 원본 RGB 798/depth 798 중 중복 없는 792쌍. `rpy`: RGB 723/depth 722 중 694쌍. 허용 시각 차이에 맞는 짝이 없는 원본 6/6개와 29/28개는 준비 단계에서 제외됐으며 `validation/data_sources.json`에 기록한다. 준비된 쌍의 무손실 처리와 원본 전체의 무손실을 혼동하지 않는다.
- 시험 Atlas: 73 키프레임, 3,312 지도 점, SHA256 `3c767d4b944708d6d05794acbfa20e51a84158b6211b259313c2ed6c2e2ab105`.
- 20,000프레임 시험은 `rpy`의 준비된 영상을 반복하고 촬영 시각을 30Hz로 재작성한 약 11분 7초 재생이다. 반복 경계는 자연스러운 연속 카메라 운동이 아니며, 추적 실패도 전체 통계에 포함한다.
- SDK 파일은 공개 영상으로 만든 소프트웨어 RGB-D 장치의 기록이다. 이미 등록된 RGB/depth, 단위 0.0002m, serial `SOFTWARE_TEST_ONLY`를 사용한다. SDK 센서 콜백·짝 구성·정렬·복사·FIFO는 실제 입력 코드로 실행하되, 물리 USB와 실제 렌즈 검증으로 주장하지 않는다.

## 회전 정확도

기준은 이 저장소의 첫 비교 빌드에서 fallback off, 1,000특징점/1스레드 실행이며, 최종 설정은 fallback on, 1,200특징점/3스레드다. 공식 원본 그대로의 ORB-SLAM3와의 비교가 아니다. 알고리즘 변경과 설정 튜닝을 합친 비교이므로 fallback 하나만의 개선 효과로 해석하지 않는다. 같은 설정의 on/off 시험도 보관하며, 그것만으로 회전 오차가 일관되게 개선됐다고 주장하지 않는다.

| 항목 | 기준 | 최종 설정 |
|---|---:|---:|
| 처리한 입력 쌍 | 694 | 694 |
| 유효 지도 pose | 645 | 647 |
| 공통 시각의 ATE RMSE | 22.14mm | 21.19mm |
| 빠른 회전 구간 RPE RMSE | 0.4906° | 0.4730° |
| 빠른 회전 구간 RPE p99 | 1.3750° | 1.2966° |

비교는 공통 유효 시각 645개 중 GT 보간 조건을 만족한 640개를 사용했다. ATE는 스케일 보정 없는 SE(3) 정렬, RPE는 인접 유효 프레임, 빠른 회전은 GT 각속도 30°/s 초과다. 이 시험에서는 위치 RMSE 약 4.3%, 회전 RPE RMSE 약 3.6%가 감소했다. `rpy`를 튜닝에도 사용했으므로 독립적인 새 환경 일반화 결과는 아니다. 실패한 47프레임에 pose를 만들어 채우지 않았다. 상세 수치는 `validation/orb3_sweep_grid_t3/common_accuracy.json`에 있다.

격자 검색 최적화 후 1,200특징점/2스레드 실행의 유효 궤적은 해당 최적화 직전 실행과 동일했다. 최종 3스레드 빌드에서도 회전 오차가 동일했고 위치 오차 차이는 수치 반올림 수준이었다. 검색 결과를 줄이지 않고 셀 벡터 복사·과도한 예약 공간만 제거했다. 1,250특징점은 유효 pose가 650개였지만 장시간 지연 여유를 위해 기본값을 1,200으로 선택했다.

## 지연과 전 프레임 처리

아래 값은 동일 프레임의 수신 대기열 진입부터 로컬 발행까지다. 구간별 p99를 더하지 않았다. 수신 p99는 같은 WSL 안의 독립 ROS 프로세스이며 LAN 수신값이 아니다.

| 20,000프레임 시험 | 유효 pose | 로컬 발행 p99 | 독립 ROS 수신 p99 | 로컬 33ms |
|---|---:|---:|---:|---|
| 초기 1,250/2 | 18,705 | 37.641ms | 38.286ms | 실패 |
| RANSAC 예산·수명 수정, 1,250/2 | 18,700 | 33.213ms | 33.762ms | 실패 |
| 특징점 1,200/2 | 18,667 | 31.052ms | 31.535ms | 통과 |
| 격자 검색 최적화·1,200/3 | 18,667 | **24.343ms** | **25.022ms** | 통과 |
| 번호 0 검사 수정 후 최종 빌드·1,200/3 | 18,667 | **24.726ms** | **25.602ms** | 통과 |

다섯 시험 모두 입력 20,000개와 수신 State 20,000개가 순서대로 일치했고, 유효 pose 수와 PoseStamped 수가 일치했다. 마지막 행의 전체 입력 p99는 25.383ms, 유효 프레임 최대값 78.908ms, 33ms 초과 유효 프레임 70개다. 1,333개 추적 실패와 91개 전체 지연 초과도 집계했다. FIFO 최대 길이는 2, 촬영·수신률은 약 30Hz, 최대 RSS는 약 608MiB였다. **p99 통과는 매 프레임 33ms 이하나 매 프레임 유효 pose를 뜻하지 않는다.**

최종 SDK와 20,000프레임 시험의 `run.json`에 기록된 실행기·native·core 해시를 `validation/build_manifest.json` 및 현재 파일과 대조했다. 모두 일치했다. 최종 결과는 `validation/orb3_soak_verified/integration.json`, `validation/orb3_soak_verified/publisher/summary.json`, `validation/orb3_sdk_verified/summary.json`에서 확인할 수 있다.

SDK 입력 시험도 실패를 포함해 보관한다. 300프레임 초기 기록의 p99는 121.007ms였고 시작 구간에 적체가 있었다. 기록 생성 시 첫 영상 디코딩을 타이머 시작 전으로 옮긴 1,500프레임/30Hz 기록에서는 다음 결과를 얻었다.

| SDK 1,500프레임 시험 | RGB/depth/처리/유효 pose | 로컬 p99 | 최대값 | 33ms 초과 |
|---|---|---:|---:|---:|
| 격자 검색 최적화 전, 1,200/2 | 모두 1,500 | 39.191ms | 67.306ms | 40 |
| 격자 검색 최적화 후, 1,200/2 | 모두 1,500 | 34.260ms | 52.612ms | 20 |
| 3스레드 확인, 1,200/3 | 모두 1,500 | 31.902ms | 50.355ms | 14 |
| 번호 0 검사 수정 후 최종 빌드, 1,200/3 | 모두 1,500 | **34.436ms** | 77.275ms | 19 |

네 시험 모두 원시 프레임 번호 누락·중복, 거부된 입력, 촬영 간격 누락이 없고 실제 수신률은 약 30Hz였다. 2스레드 최적화 후 추적 자체 p99는 26.235ms이지만 대기까지 포함한 p99는 34.260ms이므로 통과 처리하지 않았다. 2스레드 반복 시험은 p99 40.722ms였고, 별도 1/3/4스레드 비교는 각각 31.384/28.423/27.952ms였다. 단일 짧은 시험의 최솟값을 최종 성능으로 대신하지 않았다.

마지막 SDK 반복 시험의 추적 p99는 24.452ms, 대기·정렬·발행을 포함한 p99는 34.436ms였다. FIFO 최대 길이는 4, SLAM 종료 대기는 약 5ms, 최대 RSS는 약 619MiB였다. **SDK 입력 경로의 33ms 목표가 일관되게 달성됐다고 주장할 수 없다.** 50초 재생이므로 10분 장시간 입력 시험으로도 주장하지 않는다. SDK 파일 I/O와 운영체제 스케줄링도 포함된 측정이며 실제 카메라 결과는 별도 확인이 필요하다.

## 기능·장애·종료 검사

- Python 검사 13개: 카메라 YAML·ROS 파라미터 타입·잘못된 옵션·해상도·프레임률·깊이 재사용 방지·알려진 SE(3) 평가·저장된 D455 보정의 SDK/OpenCV 투영 일치.
- 네이티브 기하 검사: RANSAC 호출당 1회/전체 10회 제한, 알려진 pose 복구, mono/RGB-D 이상치 5개 배제, 밀집 셀·경계·레벨·오른쪽 카메라의 격자 검색과 전수 검색 일치. 결과 64개 초과도 전부 유지한다.
- 프레임 번호 누락, FIFO 용량 초과, 카메라 미연결은 실패 코드 3과 원인을 남기고 Atlas를 보존했다.
- 첫 SDK 프레임 번호가 0인 경우도 검사한다. 0 다음에 3이 오는 소프트웨어 장치 기록에서 기존 `last != 0` 조건이 누락을 놓치는 것을 재현했고, 수신 개수로 이전 프레임의 존재를 판단하도록 수정했다. 정상 0번 프레임을 버리지 않는다.
- 빈 영상 60개는 모두 처리하고 pose 0개로 코드 5를 반환했다. 중복 시각 입력은 코드 3, 손상 Atlas와 유효하지만 키프레임이 없는 Atlas는 입력 시작 전에 실패했다.
- 데이터 및 SDK 입력의 SIGINT는 이미 수신한 짝과 FIFO를 처리하고 10초 이내 종료했다. 정상 종료의 session mode는 `stopped`였다.
- WSL 배포판 간 실행의 신호 전달 실패를 별도로 재현하고 수정했다. 현재 작업 폴더의 진입 스크립트부터 실행해, 데이터 입력은 50/50프레임 처리 후 0.383초, SDK 입력은 48/48프레임 처리 후 0.706초에 종료 코드 0으로 끝났다. 실패 당시 보고서와 수정 후 보고서를 모두 보관한다.
- 각 localization 실행 전후 Atlas SHA256이 같았다. ROS 수신 pose 값은 CSV의 실제 추적 값과 허용 오차 1e-8 이내로 일치했고 영상·점군 토픽이 없었다.

## 재현과 증거 위치

사용법은 [README.md](README.md), 변경 근거는 [RESEARCH.md](RESEARCH.md)에 있다. 작은 JSON 보고서와 빌드 해시는 `validation/`에 보관한다. 전체 프레임 CSV·영상·SDK 기록·Atlas는 Ubuntu-22.04의 `/opt/orb-live/benchmarks`에 있으며 `validation/index.json`에서 원본 경로를 확인할 수 있다. 일반 실행의 `run.json`에는 실제 바이너리·core·지도·설정·실행기 해시가 남는다.

```bash
bash orb3_publish/test_env.sh
bash orb3_publish/tests/ransac_budget_env.sh
bash orb3_publish/tests/integration_env.sh \
  --atlas /opt/orb-live/benchmarks/orb3_publish_v1/mapping_xyz/benchmark_map.osa \
  --dataset /opt/orb-live/benchmarks/rpy_soak_30hz_20000 \
  --max-frames 20000 --output /opt/orb-live/benchmarks/my_final_soak
```

`hardware_verified=false`, `lan_latency_verified=false`, `full_requirement_verified=false`를 유지한다. 실제 카메라·사용자의 Atlas·LAN 수신·시계 오차를 포함한 검증 없이 전체 요구를 달성했다고 표시하지 않는다.

원시 번호 0의 누락 회귀 입력은 `tests/make_sdk_bag_env.sh`에 `--frames 60 --start-number 0 --gap-at 2`를 지정해 만들었다. 첫 프레임 번호는 0, 다음은 3이므로 RGB와 depth에 각각 2개 번호가 빠진 입력이다. `tests/faults.py`는 0번 프레임이 실제 처리된 것과 누락 2개가 실패로 집계된 것을 함께 검사한다.
