## 1. 결론 요약 (TL;DR)

1. **지목하신 문제 ②(포즈 뒤집힘)는 확정 — 그리고 원인은 PLY가 아니라 PEM입니다.** choco는 연속 프레임 간 회전 변화 중앙값이 **90.7°**(다른 객체 전부 3~12°). PLY 정의 오류라면 오차가 *일정*해야 하는데, 실제로는 프레임마다 90°/180°로 튑니다. **PLY 무죄, PEM 면내(in-plane) 회전 모호성 해소 실패**입니다.

2. **지목하신 문제 ①의 원인 진단은 절반만 맞습니다.** FP를 만든 건 ISM이 맞지만, **화면에 보인 `0.01`은 ISM 점수가 아니라 PEM이 스스로 낸 실패 신호**입니다. f70에서 ISM은 0.557로 자신있게 검출했고, PEM이 pose_score 0.021을 곱해 0.0117이 된 것입니다. → **PEM은 이미 "못 맞추겠다"고 경고하고 있었고, 우리 파이프라인이 그 경고를 버리고 있었습니다.**

3. **가장 큰 문제는 사실 ①②가 아니라 따로 있습니다: 갈색 택배박스 흡착(cardboard-carton attractor).** 6개 시퀀스 전부에서 choco/saffron이 장면의 큰 갈색 종이박스에 반복 발화하며, **점수 0.38~0.67의 "자신있는 오답"**이라 점수 필터로 못 거릅니다. FP 총 70건 중 최대 단일 원인입니다.

4. **좋은 소식: 지도 배치(map placement)는 건전합니다.** 709장 중 좌표계가 어긋난 건 3건뿐이고, 그 3건 모두 원인이 검출 오류(FP)입니다. → **relocalization/좌표변환 자체는 문제 없음**, 병목은 전적으로 SAM-6D 인식 단입니다.

**증거 1 — CAD 자체는 결백**

sam_105314(stride-1, 정적 객체 + 천천히 움직이는 카메라)에서 연속 프레임 간 포즈 변화:

**이 표가 핵심입니다.** choco만 회전이 90.7°씩 튀는데 **이동(t)은 28.9mm로 다른 객체와 똑같이 안정적**입니다.
- CAD 좌표계 정의가 틀렸다면 → 오차가 **모든 프레임에 동일하게** 나타나야 함 (관측과 불일치)
- 실제 관측 → **같은 물체·같은 시점인데 프레임마다 뒤집힘** (f37/38/50은 세로 오답, f158/170은 가로 정답)
- ⇒ 정적 오프셋이 아니라 **프레임별 추정 실패**

**증거 3 — 실패 양상이 "면내 회전"으로 특정됨**

| 항목 | 결과 | 해석 |
|---|---|---|
| 카메라를 향한 CAD 축 (보이는 면) | Z(39.8mm 얇은 축) **71.2%** | PEM은 *어느 면이 보이는지*는 잘 맞춤 |
| 화면 세로와 정렬된 CAD 축 | X(250mm 긴 축) **67.2%** | 그런데 *그 면을 축으로 한 회전*을 90° 틀림 |
| ISM 영상 증거 = 가로형 | 47.2% | |
| PEM 재투영 = 가로형 | **19.2%** | 세로형으로 계통적 편향 |

**물리적 원인 (가설, 미검증)**: choco는 **250 × 189.5 × 39.8mm의 납작한 판**입니다.
- 앞면 종횡비가 250:189.5 = **1.32:1로 거의 정사각형** → 형상만으로 90° 회전을 구분하기 어려움
- 게다가 얇은 판이라 **depth 포인트클라우드가 거의 평면** → 법선 축 기준 회전이 기하학적으로 거의 구속되지 않음
- SAM-6D PEM은 포인트 매칭 기반(기하 중심) → **이 축의 모호성을 풀 정보가 depth에 없음**
- ⇒ 텍스처(초코하임 인쇄면)로만 풀 수 있는데 PEM이 이를 충분히 못 쓰고 있음

이건 **형상 고유의 모호성**이라, 같은 증상이 Mugcup(12.2°/27.3%, 손잡이 빼면 회전대칭)과 milk(>70° 27.6%, 직육면체 180° 대칭)에서도 약하게 관측됩니다. **일관된 물리적 설명이 됩니다.**

> ⚠️ 위 "물리적 원인"은 관측과 정합하는 **가설**입니다. 확증하려면 §6의 검증이 필요합니다.

## 3. 문제 ① 정밀 진단 — `score 0.01`의 정체

사용자 판단: *"1번은 ISM의 문제로 판단된다"*

### 답: **FP 자체는 ISM 책임이 맞습니다. 하지만 `0.01`이라는 숫자는 ISM이 아니라 PEM이 낸 값입니다.**

**코드 근거** (`sam6d_master/SAM-6D/Pose_Estimation_Model/run_inference_custom.py:296`):
```python
pose_scores = out['pred_pose_score'] * out['score']   # PEM 포즈신뢰도 × ISM 검출점수
```
그리고 `:174`에 이미 `if det['score'] > det_score_thresh:` (기본 **0.2**) 게이트가 ISM 검출에 걸려 있습니다.
⇒ **PNG에 표시된 score는 ISM 점수가 아니라 두 값의 곱입니다.** ISM 0.2 이하는 애초에 PEM에 들어오지도 않습니다.

**지목하신 프레임 실측 분해:**

| 프레임 | ISM 점수 | PEM 출력 | 역산 pose_score | 해석 |
|---|---:|---:|---:|---|
| f37 (문제②) | 0.672 | 0.672 | **1.00** | PEM은 "확신함" — 그런데 포즈는 90° 틀림 ⚠️ |
| **f70 (문제①)** | **0.557** | **0.0117** | **0.021** | ISM이 확신하며 오검출, PEM은 "못 맞추겠다" |
| **f81 (문제①)** | **0.561** | **0.0099** | **0.018** | 동일 |
| f146 | 0.661 | 0.000 | 0.000 | 박스는 정확해 보이는데 pose_score 0 (오탐 기각) |

**즉 f70/f81에서 벌어진 일:**
1. ISM이 갈색 택배박스를 choco로 **0.56에 오검출** ← **여기가 진짜 ISM 문제**
2. PEM이 그 위에 포즈를 맞추려다 실패, **pose_score 0.02로 스스로 경고**
3. 우리 파이프라인이 그 경고를 **필터링 없이 그대로 렌더링** ← **여기가 파이프라인 문제**

> ## ⚠️ 2026-07-15 정정 (§9 참조)
> 아래 "pose_score는 쓸만한 신호" 결론은 **과대평가였습니다.** pose_score는 *기하 피팅 붕괴*는 잡지만 ***객체가 틀렸는지는 전혀 못 잡습니다.***
> 실측: 민무늬 갈색 택배박스에 pose_score **0.99~1.00**. 코드상 pose_score에 텍스처가 **구조적으로 0% 반영**됩니다. §9에 전체 분석.

**PEM pose_score는 쓸만한 신호인가? (1,700건 전수 검증)**

| 역산 pose_score | n | IoU 중앙값 | IoU<0.3(붕괴) 비율 |
|---|---:|---:|---:|
| **[0.00, 0.05)** | 51 | **0.190** | **78.4%** |
| [0.05, 0.20) | 36 | 0.590 | 27.8% |
| [0.20, 0.50) | 76 | 0.662 | 9.2% |
| [0.50, 0.80) | 358 | 0.721 | 4.7% |
| [0.80, 1.00] | 1,179 | 0.712 | 0.9% |

Pearson r = 0.454. → **pose_score < 0.05는 78%가 실제로 깨진 포즈**입니다. **지금 버리고 있는 무료 신호**입니다.
단, f146처럼 **정상 포즈인데 0.0인 오탐 기각도 존재**하므로 무손실은 아닙니다.

**한편 최종 표시 score로는 필터가 안 됩니다:**

| 표시 score | n | IoU 중앙값 |
|---|---:|---:|
| [0.00, 0.05) | 58 | **0.201** |
| [0.05, 0.10) | 16 | 0.592 |
| [0.30, 0.50) | 302 | 0.693 |
| [0.50, 0.70) | 961 | 0.719 |
| [0.70, 1.00] | 284 | 0.723 |

**0.05 위로는 완전히 평평합니다(0.59~0.72).** 즉 **표시 score를 0.4 같은 값으로 올려도 포즈 품질은 전혀 좋아지지 않습니다.** 0.05 미만만 의미 있게 나쁩니다. 이건 중요한 함정입니다 — 육안 검사에서도 *"score 0.00인데 박스는 정확"* (105314 f146 choco, f398 Mugcup) 사례가 나왔습니다.

**추가 실패 모드 — t=0 퇴화 포즈**: 13건이 **translation이 정확히 (0,0,0)mm**입니다. 이건 `T_map_obj = T_map_cam × T_cam_obj`에서 **객체를 카메라 위치에 그대로 박아넣어** 지도를 오염시킵니다. 전부 pose_score 0이라 위 게이트로 같이 걸러집니다.

### 4-2. 🟠 saffron 환각 — 진짜 객체가 가려지면 아무 데나 찍음

가장 신뢰도 높은 객체(중앙값 0.752)이면서 동시에 FP 최다 배출. **양극단(bimodal)**입니다.
- 실제 샤프란 병이 보이면 → 0.71~0.82로 정확 (110633 f031/107/230/306)
- 병이 가려지거나 없으면 → 종이박스 빈 면에 **0.35~0.76으로 환각** (110532에서만 7건: 0.00, 0.12, 0.32, 0.33, 0.64, 0.66, 0.72)

→ **높은 score가 "객체가 존재함"을 보장하지 않습니다.**

### 4-3. 🟠 봉제인형 클래스 혼선 (Bear / Rabbit / Dinosaur)

같은 인형에 프레임마다 다른 라벨:

- 초록 공룡 → `Bear 0.44`(110104 f404), `Bear 0.56`(105314 f110), `Febreze_high 0.35`(110532 f039)

> *"the DINOv2 semantic/masked-appe gates do NOT discriminate between plush toys (all round matte blobs -> any toy box passes every toy's gates). The ONLY discriminative stage is YOLO-World prompt firing."*

즉 인형 간 구분은 **YOLO-World 프롬프트 발화 하나에만** 의존하는 구조이고, 그게 흔들리면 곧바로 오라벨입니다. §2의 안정성 표에서 Bear가 >70° 14.8%로 튀는 것도 이와 무관하지 않습니다.

### 4-4. 🟡 클래스 간 중복 라벨 — 한 물체에 여러 박스

한 이미지 영역에 2개 이상 클래스가 동시에 박스를 그림 (총 9건+):

## 9. 추가 분석 — "PEM은 왜 CAD 텍스처로 갈색 박스를 못 거르나?" (2026-07-15 추가)

사용자 질문: *"PLY 모델의 텍스처 정보를 활용하여 충분히 걸러낼 수 있어야 한다고 생각하는데 그러지 못하는 이유가 뭐지? 갈색 흰색 줄무늬에 '초코하임' 글자도 있는데 단순 갈색 면 박스는 걸러낼 수 있어야 하는 것 아닌가?"*

**결론: 지적이 타당합니다. 텍스처는 실제로 존재하고 PEM이 로드까지 하는데, 구조적으로 "판정"에는 쓰이지 않습니다.**

### 9-0. ⚠️ §3 결론 정정

먼저 §3에서 제가 내린 *"pose_score < 0.05 게이트가 유효하다"*는 결론을 정정합니다. 통계 자체(pose_score<0.05 → 78%가 IoU<0.3)는 맞지만 **해석이 틀렸습니다.**

| 대상 | 역산 pose_score |
|---|---|
| f2 민무늬 갈색 택배박스 (FP) | **0.991** |
| f434 민무늬 갈색 택배박스 (FP) | **1.000** |
| f494 민무늬 갈색 택배박스 (FP) | **0.958** |
| f350 / f410 갈색 택배박스 (FP) | 0.813 / 0.819 |
| f86 / f206 / f506 갈색 택배박스 (FP) | 0.678 / 0.681 / 0.671 |
| f70 / f81 갈색 택배박스 (FP) | 0.021 / 0.018 |
| f158 / f170 진짜 초코하임 (정답) | 1.000 / 1.000 |
| f37 / f38 / f50 진짜 초코하임 (**90° 오답**) | **1.000 / 1.000 / 1.000** |
| f146 진짜 초코하임 (**박스 정확**) | **0.000** |

**pose_score는 "객체가 맞는가"와 사실상 무관합니다.** 민무늬 택배박스에 1.000을 주고, 정확한 검출(f146)에 0.000을 줍니다. 이게 잡아내는 건 *기하 피팅이 붕괴했는가*(§3의 IoU<0.3 = ISM 마스크와 포즈 불일치)뿐이고, **§4-1 택배박스 흡착은 전혀 못 잡습니다.** → §7의 방어선 A는 t=0 퇴화 포즈 13건 제거 정도로 효과가 축소됩니다.

### 9-1. 이유 ① — pose_score 계산식에 색이 아예 없음

`Pose_Estimation_Model/utils/model_utils.py:277-282`:
```python
pred_pts = (pts1 - pred_t.unsqueeze(1)) @ pred_R                    # 장면 점 → CAD 좌표계
dis = torch.sqrt(pairwise_distance(pred_pts, model_pts)).min(2)[0]  # 최근접 CAD '점'까지 거리
mask = (label1>0).float()
pose_score = (dis < dis_thres).float()
pose_score = (pose_score * mask).sum(1) / (mask.sum(1) + 1e-8)
```
**pose_score = "장면 점 중 몇 %가 CAD 점에서 `dis_thres` 이내인가" = 순수 기하 inlier 비율.**

그리고 `model_pts`의 출처 (`run_inference_custom.py:188`):
```python
model_points = mesh.sample(cfg.n_sample_model_point).astype(np.float32) / 1000.0
```
`trimesh.sample()`은 **표면 XYZ만 뽑고 색/텍스처를 버립니다.** → 텍스처가 신뢰도 판정에 반영될 경로가 **구조적으로 존재하지 않습니다.**

### 9-2. 이유 ② — PEM은 "맞추는" 모델이지 "판정하는" 모델이 아님

텍스처를 **쓰긴 씁니다.** `feature_extraction.py:126,129`에 `self.rgb_net = ViT_AE(cfg)` / `rgb = end_points['rgb']`가 있고, `_get_template()`(`run_inference_custom.py:121-150`)이 템플릿 `rgb_<i>.png`를 42뷰 전부 로드합니다.

**그러나 텍스처의 역할은 "대응점 찾기(correspondence)"까지입니다.** 파이프라인은:
```
ViT(RGB) + 기하 인코더 → coarse/fine point matching → Weighted Procrustes(SVD) → R, t
```
출력은 **R, t뿐**입니다. *"이게 그 객체가 맞는가"를 판정하는 head가 없습니다.* PEM은 MegaPose 합성데이터로 학습됐고, 그 학습 세팅에서 **검출은 항상 옳다고 가정**합니다. 즉 **거부(reject)라는 개념이 아키텍처에 없습니다.** 마스크를 주면 무조건 그 안에 포즈를 맞춥니다.

⇒ 텍스처 기반 필터링을 기대할 위치는 PEM이 아니라 **ISM**입니다(§9-4).

### 9-3. 이유 ③ — choco는 기하가 퇴화 형상이라 "민무늬 박스 = 초코하임"

`dis_thres`는 절대 미터가 아니라 **객체 반경으로 정규화된 값**입니다 (`fine_point_matching.py:76`이 `end_points['model'] / radius`를 넘김, `compute_fine_Rt` 기본값 0.15).

| 항목 | 값 |
|---|---|
| choco 모델 반경 | 157.1 mm |
| 실제 `dis_thres` = 0.15 × 157.1 | **23.6 mm** |
| choco 두께(Z) | 39.8 mm |
| 허용 껍질 두께 = 39.8 + 2×23.6 | **≈ 87 mm** (자기 두께의 2.2배) |

**납작한 판(250×189.5×39.8mm)에 ±23.6mm 허용을 주면, 대략 평면인 아무 표면 패치나 inlier가 됩니다.** 갈색 택배박스의 평평한 면 = 기하학적으로 초코하임 판과 **구별 불가**입니다. → pose_score 0.99~1.00.

**이게 §2의 90° 뒤집힘이 pose_score 1.0을 받는 이유이기도 합니다.** 250×189.5 판을 면내로 90° 돌려도 점들은 여전히 서로 23.6mm 안에 들어옵니다. **기하는 뒤집힘을 볼 수 없습니다.** 뒤집힘을 구분할 수 있는 유일한 정보가 바로 사용자가 지적한 "초코하임" 글자 방향인데, **그게 점수에 안 들어갑니다.** ⇒ §2와 §4-1은 사실 **같은 뿌리(텍스처가 점수에서 배제됨)의 두 증상**입니다.

### 9-4. 그럼 ISM은 왜 못 걸렀나 — 텍스처가 있는데도

ISM은 텍스처 비교 장치를 갖고 있습니다(DINOv2 semantic gate 0.35 + MobileSAM masked-appe gate 0.55). 그런데 갈색 택배박스를 **0.56으로 통과**시켰습니다. 실측 색 비교:

| 대상 | 관측 RGB 평균 | HSV Value |
|---|---|---|
| f158 **진짜 초코하임** (정답) | [82, 73, 63] | 82 |
| f170 **진짜 초코하임** (정답) | [72, 65, 57] | 72 |
| f70 민무늬 **갈색 택배박스** (FP) | [88, 76, 62] | 88 |
| f81 민무늬 **갈색 택배박스** (FP) | [87, 71, 58] | 87 |
| f434 민무늬 **갈색 택배박스** (FP) | [93, 72, 57] | 93 |
| **템플릿 렌더** `rgb_0.png` | **[171, 148, 140]** | **171** |

**두 가지가 동시에 드러납니다:**

1. **실제 장면에서 초코하임과 택배박스는 색이 거의 같습니다** ([82,73,63] vs [88,76,62]). 조명이 어두워 둘 다 어둑한 갈색 덩어리입니다. → **색만으로는 원리적으로 분리 불가.** 남는 단서는 "초코하임" 글자/줄무늬 같은 **미세 텍스처**뿐입니다.

2. **템플릿 렌더가 실물보다 2배 이상 밝습니다** (Value 171 vs 82). 채도도 48.7/255로 낮아, 렌더 평균색 [171,148,140]은 **바랜 베이지-핑크 = 오히려 판지 색**에 가깝습니다. 실물 초코하임의 진한 마룬/골드가 재현되지 않았습니다. → **템플릿↔실물 도메인 갭이 큽니다.**

⇒ 즉 ISM의 appearance 게이트는 *"밝고 바랜 렌더"* vs *"어둑한 실제 크롭"*을 비교하고 있고, 정작 구분해야 할 두 대상(초코하임 vs 판지)은 실제 장면에서 색이 사실상 동일합니다.

> ### ⚠️ 이 "도메인 갭" 가설은 §10에서 **검증 결과 기각**되었습니다.
> 텍스처 판별은 **이미 정상 작동 중**이었고, 진짜 원인은 **`appe_gate=0.55`의 오설정**이었습니다. §10 참조.

### 9-5. 요약 — 텍스처가 판정에 못 쓰이는 3단 구조

| 단계 | 텍스처 사용? | 판정 능력 |
|---|---|---|
| **ISM** YOLO-World 프롬프트 | ❌ (`"maroon box"` 텍스트뿐) | 갈색 택배박스 발화 |
| **ISM** DINOv2 cls / masked-appe | ✅ 사용 | **통과시킴 (0.56)** — 렌더 도메인 갭 + 실물 색 동일 (§9-4) |
| **PEM** ViT_AE(template rgb) | ✅ 사용 | 대응점 찾기 **전용**, 판정 head 없음 (§9-2) |

**"초코하임 글자를 보고 거른다"는 판정을 하는 주체가 파이프라인 전체에 아무도 없습니다.** 텍스처는 두 번 로드되지만, 한 번은 도메인 갭 때문에 무력화되고(ISM), 한 번은 판정이 아닌 매칭에만 쓰입니다(PEM).

## 12. "객체별 스윕"이 무슨 뜻인가 — 그리고 왜 전역 게이트가 불가능한가

| Sauce_high | 167 | 0.554 | 0.649 | **0.677** | 0.701 | 0.772 |
| Dinosaur | 91 | 0.556 | 0.633 | **0.659** | 0.679 | 0.709 |

### 12-2. 실측된 객체별 경계 — 전부 다릅니다

육안 감사로 라벨링한 프레임의 appe:

**세 객체, 세 개의 다른 경계.** 이게 "각자 스윕"의 뜻입니다 — 객체마다 자기 데이터에서 자기 골짜기를 찾아야 합니다.

### 12-3. 전역 게이트가 **수학적으로 불가능**한 증거

```
choco   전체 검출 범위 : 0.550 .. 0.712   (경계 ~0.59)
saffron 전체 검출 범위 : 0.553 .. 0.838   (경계 ~0.72)

choco의 최댓값(0.712) < saffron의 경계(0.72)
```

| 전역 게이트 | choco | saffron |
|---|---|---|
| 0.59 | ✅ FP 대부분 제거 | ❌ FP(최대 0.724) **전부 생존** |
| 0.72 | ❌ **275/275 전멸** (진짜 포함) | ✅ FP 제거 |

**두 객체의 동작 구간이 겹치지도 않습니다.** 하나의 전역 임계로 둘 다 만족시키는 건 불가능합니다. → 반드시 `objects[]`의 **객체별 override**로만.

### 12-4. 인형은 스윕해도 **안 됩니다** — 그리고 그게 스윕의 결론입니다

Bear/Rabbit/Dinosaur는 사정이 다릅니다. 육안 감사로 라벨링한 프레임의 appe:

| 그룹 | n | min | 중앙값 | max |
|---|---:|---:|---:|---:|
| **오라벨** (흰토끼를 Dinosaur, 초록공룡을 Bear 등) | 9 | 0.625 | **0.684** | 0.726 |
| **정답** (진짜 곰/공룡) | 6 | 0.600 | **0.688** | 0.758 |

**중앙값이 0.684 vs 0.688로 사실상 동일하고 범위가 완전히 겹칩니다. 골짜기가 없습니다.** → **어떤 appe 임계로도 인형 혼선은 못 고칩니다.**

이건 config가 이미 경고한 내용과 정확히 일치합니다:
> *"the DINOv2 semantic/masked-appe gates do NOT discriminate between plush toys (all round matte blobs -> any toy box passes every toy's gates). The ONLY discriminative stage is YOLO-World prompt firing."*

⇒ **인형의 "스윕"은 임계를 찾는 작업이 아니라 "임계로 풀리는 문제가 아님을 확인하는 작업"입니다.** 결론이 나오면 해법은 다른 곳(YOLO 프롬프트 재설계 / 객체별 `score_threshold`)입니다. 즉 choco·saffron·milk는 **게이트 문제**, 인형은 **프롬프트 문제**로 성격이 다릅니다.

## 13. frame 146의 milk는 왜 생겼나

사용자 질문: *"frame 146에 milk도 갑자기 왜 생긴건지"*

### 13-1. 무엇에 붙었나

`ism_milk.png`를 보면 milk 박스가 붙은 대상은 **비닐로 싸인 커다란 하얀 iPTIME 상자**입니다 (진짜 초코하임은 테이블 왼쪽 앞의 갈색 박스). 그리고 milk 템플릿은 **하늘색/흰색 우유팩**(`Milk_scaled_195mm`), config 프롬프트는 `yolo_prompt: "milk carton"`.

### 13-2. 왜 게이트를 통과했나 — **0.0069 차이로**

| 단계 | 값 | 결과 |
|---|---|---|
| YOLO-World `"milk carton"` | 하얀 네모 상자에 발화 | 통과 |
| DINOv2 semantic gate (0.35) | — | 통과 |

- **TP: 0.641 ~ 0.731** (중앙 0.683)

**`appe_gate: 0.63`이면 5개 FP 전부 제거되고 4개 TP 전부 유지됩니다.**

⇒ **"갑자기 생긴" 게 아니라, 게이트가 FP 무리 아래에 있어서 원래부터 통과하고 있던 것**입니다. f146이 눈에 띈 이유는 단지 PEM이 pose_score 0.036으로 실패를 신고해 표시 점수가 0.02로 튀었기 때문입니다. **표시 점수가 높은 FP(§4-1의 0.38~0.67)가 오히려 더 위험합니다** — 조용히 통과하니까요.

```python
accepted_res.sort(key=lambda t: t[1]["best_yolo"], reverse=True)

for o, r in accepted_res:
    if any(_iou_xyxy(r["box"], rk["box"]) > 0.5 for _, rk in kept):
        continue                 # 억제
    kept.append((o, r))
```

**핵심: 이 NMS는 `accepted`된 검출들 사이에서만 작동합니다.** 어떤 객체가 appe 게이트에서 탈락하면 `accepted_res`에서 빠지고 → **그 객체가 억제하던 다른 객체가 풀려납니다.**

### 14-4. 함의 — FP는 "쌓여" 있습니다 (두더지잡기)

문제의 박스는 **saffron이 환각하던 택배박스의 빈 면**입니다. 따라서 **새로 나온 Febreze 3건도 거의 확실히 FP**입니다. 게다가 Febreze의 appe(0.5595~0.5851)는 자기 분포의 저-꼬리(§12-1: median 0.658, p25 0.618)라 FP 특징과 일치합니다.

⇒ **§4-1의 택배박스 흡착은 측정된 것보다 심각합니다.** choco·saffron만의 문제가 아니라 **여러 객체가 같은 택배박스에 줄 서서 발화하고 있고, NMS가 그때그때 1등만 보여주고 있었습니다.** 1등을 게이트로 치우면 2등이 올라옵니다.

**이것이 §10-5의 "객체별 스윕" 한계를 넘어서는 새로운 제약입니다:**
- 게이트를 **한 객체씩 순차 적용하면 두더지잡기**가 됩니다.
- **10개 객체 전부의 경계를 동시에 정해야** 실제 FP가 줄어듭니다.
- 혹은 근본 원인(택배박스가 모든 객체를 끌어당김 = YOLO 프롬프트 단계)을 쳐야 합니다.

**§13-3의 "표시 점수 높은 FP가 더 위험하다"에 하나 더 추가**: NMS에 가려진 FP는 아예 보이지도 않습니다. 우리가 센 FP 70건은 **각 프레임·각 박스의 1등만 센 값**입니다.

⇒ **§12-1의 히스토그램이 이미 경고하고 있었습니다** (`saffron |++#+###++#.##|` = 골짜기 없음, `choco |##++####...|` = 명확한 골짜기). 저는 이 신호를 과소평가하고 소표본 라벨을 믿었습니다.

```yaml

```

**교훈 (3단계로 틀렸습니다)**:
1. §12-2: 소표본 라벨의 min/max를 경계로 삼음 → milk/saffron 붕괴
2. §10-3: 전수 히스토그램의 골짜기로 보정 → **표본이 단일 데이터셋 편중이면 골짜기도 가짜**
3. ⇒ 게이트 검증은 **모든 데이터셋에서 독립적으로 골짜기가 재현될 때만** 유효

# 15. 우선순위 ① 수정 시도 — 가설 반증, 진짜 원인 발견

§14-17에서 1순위로 지목한 **"객체당 프레임당 단일 슬롯"** 수정을 구현하고 실측했습니다. 전수(2,596프레임) 대신 **§14-16/14-17이 근거로 지목한 문제 프레임 61장 + 육안 확증 대조군 16장 = 75장**만 사용했습니다.

## 15-1. ⚠️ 정정: 단일 슬롯은 원인이 아니었습니다

`yolo_ism_object_n.recognize_multi()`를 구현해 게이트를 통과한 **모든** proposal을 내보내도록 하고 61프레임에 적용한 결과:

| | baseline(단일 슬롯) | `--multi` |
|---|---:|---:|
| 검출 | 151 | 160 (+9) |
| **새로 살아난 객체(FN 회복)** | — | **0건** |
| 추가된 박스 | — | choco 9, Sikhye 1, Bear 1 |

**FN 회복이 0건입니다.** 육안 확인 결과 **추가된 choco 박스 9개는 전부 민무늬 갈색 택배박스(FP)**였고, baseline은 이미 진짜 초코하임을 잡고 있었습니다(`<scratchpad>/choco_new.png`).

**이유**: 단일 슬롯은 argmax-**semantic**으로 승자를 뽑는데, 그게 이미 진짜를 고르고 있었습니다. 슬롯을 풀면 택배박스 FP가 **풀려날 뿐**입니다. → **단일 슬롯은 choco에서 오히려 방어 역할을 하고 있었습니다.** §14-16의 "진짜 choco가 택배박스로 이주" 서사는 f344 같은 개별 사례로는 맞지만, **그 메커니즘이 단일 슬롯이라는 진단은 틀렸습니다.**

`--multi`는 기본값 off로 유지합니다(2차 인스턴스 연구용으로 코드는 보존).
