# 실시간 SAM-6D 설계 (bag 재생 → 구독 → 포즈 추정 반복)

작성일: 2026-08-13 (v2 — 사용자 요구 5개항 반영, 쉬운 말 판)
대상: `integration/` 2단계(SAM-6D)를 실시간 방식으로 바꾸기
선행: 어제 끝낸 ORB-SLAM3 실시간 전환(같은 방식을 SAM에 적용)

---

## 0. 사용자가 원하는 것 (확정)

1. `data_slam`의 bag을 `ros2 bag play`로 틀어서 카메라가 지금 찍는 것처럼 만든다.
2. SAM-6D를 ROS2 노드로 띄워서 그 화면을 받아 물체 포즈를 추정한다(ISM + PEM).
3. 한 장을 다 처리하고 나면 **그 순간 들어와 있는 최신 화면**을 받아 다시 처리한다. 모든 프레임을 처리하지 않는다.
4. (나중에) object-memory가 3번 결과와 SLAM 위치를 합쳐 SLAM 지도 위에 물체를 등록한다.
5. SAM-6D를 **새로 만드는 conda 환경 `sam6d`(ROS 2 Jazzy)** 안에서 돌린다. 지금의 humble 환경은 쓰지 않는다.

---

## 1. 지금 뭐가 문제인가 (쉬운 말)

### 문제 A. 지금 SAM-6D는 "파일을 통째로 읽는 프로그램"이다

현재 `integration`이 쓰는 SAM-6D는 두 개의 배치 프로그램이다.

- `build_pem_inputs.py` — bag **파일을 직접 열어서** 10장에 1장씩 뽑아 물체를 찾는다(ISM).
- `run_pem_batch.py` — 앞에서 만든 폴더를 훑어 물체마다 포즈를 구한다(PEM).

즉 **화면을 "받는" 개념이 없다.** 파일을 처음부터 끝까지 읽고 끝난다. 그래서 1~3번을 그대로는 못 한다.

### 문제 B. 그런데 실시간 노드가 이미 하나 있다 (6월에 만든 것)

`sam6d_ws/src/sam6d_ros/sam6d_ros/sam6d_multiobject_node.py`

- 모델(DINOv2, MobileSAM, PEM, 물체별 템플릿)을 **켤 때 한 번만** 올려놓고,
- RGB + depth가 들어올 때마다 물체를 찾고 포즈까지 구한다.

이게 우리가 원하는 2번의 뼈대다. **새로 만들 필요가 없다.** 다만 아래 다섯 가지가 어긋나 있다.

| | 어긋난 점 | 쉬운 설명 | 결과 |
|---|---|---|---|
| 1 | YOLO가 화면을 **640 크기로 줄여서** 본다 | 지금 쓰는 설정 파일에는 960으로 보라고 적혀 있다. 실시간 쪽만 640에 고정돼 있다 | 같은 장면인데 **실시간이 멀리 있는 물체를 더 못 찾는다**. 오프라인 쪽은 이미 같은 실수를 발견해 고친 적이 있다 |
| 2 | 물체를 **하나씩 따로** 판단하고 끝낸다 | 7월에 추가한 "한 상자에 이름이 두 개 붙으면 하나만 남기는" 정리 단계가 실시간 경로에는 없다 | **오검출이 늘어난다**(같은 갈색 상자에 초코+택배박스 두 라벨) |
| 3 | 결과를 **이름 없이** 내보낸다 | 포즈 목록만 보내고 "이게 우유다/초코다"라는 이름과 점수가 빠진다 | **4번(object-memory 등록)을 아예 할 수 없다** |
| 4 | 들어온 화면을 **줄 세워서** 처리한다 | 처리 속도보다 화면이 빨리 들어오면 대기줄이 계속 길어진다 | 시간이 갈수록 **점점 옛날 화면**을 처리한다. 3번 요구와 정반대 |
| 5 | 실행이 **수동 3단계**다 | YOLO 보조 프로그램 먼저 → 노드 → bag 재생을 사람이 순서대로 띄워야 한다 | 재현이 어렵고 종료 시점도 제멋대로 |

### 문제 C. 5번 요구(Jazzy 새 환경)가 바꾸는 것

지금 구조가 이상하게 생긴 이유가 하나 있다. **현재 humble 환경의 YOLO 버전이 낡아서(8.0) YOLO-World를 못 돌린다.** 그래서 YOLO만 다른 환경(`sam_yolo`, 8.4)에서 **별도 프로그램으로 띄우고 소켓으로 사진을 주고받는** 우회를 하고 있다(위 문제 5, 그리고 문제 1의 원인도 여기다).

**새 환경 `sam6d`를 만들면 그 환경에 최신 YOLO를 그냥 깔면 된다 → 보조 프로그램과 소켓이 통째로 사라진다.** 프로세스가 2개에서 1개로 줄고, 640/960 문제도 자연히 없어진다. 이게 5번 요구의 가장 큰 실익이다.

두 번째 실익: ORB-SLAM3 실시간이 이미 Jazzy(`orb3slam`)다. SAM도 Jazzy면 **4번에서 둘을 붙일 때 배포판이 같다.** humble ↔ jazzy 혼용이면 나중에 통신 문제를 따로 검증해야 한다.

대신 **새 위험**이 하나 생긴다 → 다음 절.

## 2. 새 환경 `sam6d`에서 확인해야 할 것 (가장 큰 불확실성)

PEM에는 **직접 컴파일해야 하는 CUDA 코드**가 들어 있다(`pointnet2`). 지금 humble 환경에는 `pointnet2-0.0.0-py3.11-linux-x86_64.egg`로 이미 빌드되어 있는데, 이건 **파이썬 3.11 + torch 2.7.1(cu12.9) 전용**이라 새 환경에서는 **다시 컴파일해야 한다.**

현재 확인된 사실:

| 항목 | 현재 humble 환경 | 새 `sam6d` (Jazzy) 예상 |
|---|---|---|
| Python | 3.11.15 | **3.12** (RoboStack Jazzy 기준, `orb3slam`이 3.12.13) |
| torch | 2.7.1 + cu12.9 | 같은 계열로 맞춘다(Blackwell GPU라 최소 cu12.8) |
| nvcc | conda 안에 12.9 있음 | **conda로 같이 설치 필요** |
| ultralytics | 8.0.135 (YOLO-World 불가) | **8.4 설치 → 사이드카 제거** |
| gorilla-core, timm, segment_anything | 설치됨 | 동일 설치 |
| pointnet2 | 빌드됨(py3.11) | **재빌드 필요 ← 유일한 진짜 위험** |

→ 그래서 **첫 작업(S0)은 "환경을 만들고 사진 한 장으로 ISM+PEM이 도는지" 확인**이다. 여기서 막히면 그 아래 설계는 전부 무의미하다. 만약 py3.12에서 pointnet2 빌드가 깨지면, 대안은 `sam6d` 환경을 **Jazzy + Python 3.11**로 만드는 것이다(RoboStack이 3.11 조합을 제공하면). 그것도 안 되면 5번 요구를 재검토해야 한다.

## 3. 만들 구조

```
ros2 launch sam6d_ros sam6d_realtime.launch.py config:=<설정.yaml>        (env: sam6d / Jazzy)
│
├─(1) SAM-6D 노드 하나                     ← 사이드카 없음, 프로세스 1개
│       받는 것 : /camera/camera/color/image_raw
│                 /camera/camera/aligned_depth_to_color/image_raw
│                 /camera/camera/color/camera_info
│       내는 것 : /sam6d/detections   (물체 이름 + 점수 + 포즈)
│                 /sam6d/status       (지금 몇 Hz로 처리 중인지, 몇 장 건너뛰었는지)
│       파일    : detections.jsonl, frames.jsonl, run_meta.json
│
├─(2) 준비 완료 대기: ros2 topic echo --once /sam6d/status
│       └ 끝나면 ─→ (3)
│
└─(3) ros2 bag play <sam bag> --clock --rate 1.0
        └ bag 끝 ─→ 노드에 종료 신호 ─→ 노드 종료 ─→ launch 종료
```

**왜 이렇게 하나**

- **런치 하나로 bag 재생까지 묶는다** — ORB3에서 이미 검증한 방식. 사람이 순서를 맞출 필요가 없고, bag이 끝나면 알아서 정리하고 꺼진다.
- **"준비 완료 대기"를 고정 시간 대신 쓴다** — ORB3는 12초 기다리면 됐지만 SAM은 모델 로드가 수십 초라 고정 시간은 앞부분 화면을 통째로 버린다. `ros2 topic echo --once`는 첫 메시지가 올 때까지 기다리므로 **새 스크립트 없이** 이 문제가 풀린다.
- ORB3 실시간이 도메인 71을 쓰므로 SAM은 **도메인 72**로 분리(동시에 돌려도 안 섞이게).

## 4. 3번 요구(모든 프레임 처리 안 함)를 어떻게 구현하나

이게 이 설계의 심장이다. 규칙은 한 줄이다.

> **처리 중일 때 들어온 화면은 그냥 버린다. 처리가 끝나면 그 시점의 가장 최신 화면부터 다시 시작한다.**

구현:

- 구독 설정을 **깊이 1 / best-effort**로 둔다 → ROS가 알아서 오래된 것을 버리고 최신 것만 남긴다.
- RGB와 depth 짝 맞추기 큐도 **2장**으로 줄인다(30 Hz에서 2장 넘어가면 어차피 낡은 화면이다).
- 노드 안에 `busy` 표시를 둬서, 처리 중 도착한 짝은 세기만 하고 버린다.
- 버린 장수와 실제 처리 Hz를 `/sam6d/status`에 계속 내보낸다 → **"제대로 실시간인지"를 눈으로 확인할 수 있게** 한다.

판정 기준: `rate 1.0`으로 틀었을 때 **(지금 시각 − 처리한 화면의 촬영 시각)이 시간이 지나도 커지지 않아야 한다.** 커지면 대기줄이 밀리고 있다는 뜻이다.

참고: 버리는 것 자체는 문제가 아니다. 예전 실측에서 물체 지도를 만드는 데는 초당 1~3장이면 충분했다.

## 5. 결과를 어떤 형태로 내보내나

**토픽 — `/sam6d/detections` (`vision_msgs/Detection3DArray`)**

- 시각(`header.stamp`) = 그 화면을 **찍은 시각**(받은 시각이 아니다). 4번에서 SLAM 위치와 짝지으려면 이게 필수다.
- 검출마다: 물체 **이름**, **점수**, **카메라 기준 포즈**(미터).
- 지도 좌표로 바꾸지 않고 **카메라 기준 그대로** 보낸다. 지도 좌표 변환은 object-memory가 "그 화면을 찍던 순간의 SLAM 위치"를 찾아서 하는 일이다(늦게 도착한 검출을 옳게 처리하는 유일한 방법).

이 형식은 이미 `objectmemory_ws`의 라이브 노드가 기다리고 있는 형식이라, **이걸 내보내는 순간 4번의 배선이 절반 끝난다.**

**파일 — 나중에 오프라인과 비교하려면 필요**

```
detections.jsonl  검출 한 건 = 한 줄 (찍은 시각, 물체, 점수, R, t, 박스, 단계별 소요 ms)
frames.jsonl      처리한 화면 한 장 = 한 줄 (찍은 시각, 검출 수, 소요 ms, 그동안 버린 장수)
run_meta.json     설정·물체 목록·카메라 내부값·bag 경로·시작/종료 시각
```

이걸 접어서 기존 `sam/objects.json`과 **똑같은 형식**으로 만들어 주면, 그 아래(물체 지도 만들기·영상 만들기)는 **코드를 하나도 안 고치고** 그대로 쓸 수 있다. 단 화면을 건너뛰기 때문에 "몇 번째 화면"이라는 번호가 오프라인과 달라지므로, 노드가 실제 처리한 시각 목록(`timestamps_rt.json`)을 같이 남기고 `integration/pipeline/sam6d.py`에 세 줄짜리 분기만 넣는다.

## 6. 실행 방법 (목표 모습)

```bash
conda activate sam6d
export ROS_DOMAIN_ID=72
ros2 launch sam6d_ros sam6d_realtime.launch.py \
     config:=/.../sam6d_ws/configs/rt_0807_185223.yaml
```

설정 파일 한 개에 bag 경로 / 재생 속도 / 토픽 이름 / 대상 물체 / 출력 폴더가 전부 들어간다(ORB3 run config와 같은 구조).

integration 쪽은 기존 사용법을 그대로 두고 모드만 추가한다.

```bash
python3 integration/pipeline/sam6d.py 185223__circle_ccw_8laps            # 지금 방식(그대로)
python3 integration/pipeline/sam6d.py 185223__circle_ccw_8laps --realtime  # 새 방식
```

## 7. 작업 순서

| 순서 | 할 일 | 끝났다고 말할 수 있는 조건 |
|---|---|---|
| **S0** | **`sam6d` (Jazzy) 환경 만들기** — RoboStack Jazzy + torch(cu12.x) + nvcc + ultralytics 8.4 + timm/gorilla/segment_anything + **pointnet2 재빌드** | 그 환경에서 **사진 한 장**에 ISM+PEM이 돌아 포즈가 나온다. YOLO-World가 사이드카 없이 직접 뜬다 |
| **S1** | 노드를 새 환경으로 옮기고 **사이드카 제거** + **최신 화면만 처리(3번)** + 이름 있는 출력 | bag을 틀면 노드가 초당 N장 처리하고, 처리 지연이 시간이 지나도 늘지 않는다. `ros2 topic echo /sam6d/detections`에 물체 이름이 보인다 |
| **S2** | **결과 맞추기** — 물체별 개별 판단을 오프라인과 같은 `recognize_frame_auto`로 교체(위 문제 2) | 같은 bag의 같은 화면에서 **오프라인이 찾은 것과 실시간이 찾은 것이 99% 이상 일치**. 다른 것은 전부 열거해 이유를 밝힌다 |
| **S3** | **런치 파일** — 노드 + bag 재생 + 준비 대기 + 자동 종료 | 명령 한 줄로 시작해서 사람 손 없이 끝까지 돈다 |
| **S4** | **integration 연결** — `--realtime` 모드 + 결과 변환 | 같은 세션을 오프라인/실시간으로 각각 돌려 물체 지도를 비교한 표가 나온다 |
| **S5**(나중) | **4번** — SLAM 위치 + 검출을 object-memory로 합치기 | 지도 좌표에 물체가 등록된다 |

**S2를 S3보다 먼저** 하는 이유: 런치부터 만들면 "실시간이 오프라인보다 결과가 나쁘다"는 상황이 왔을 때, 화면을 건너뛰어서인지 알고리즘이 달라서인지 구분할 수 없다.

## 8. 위험 목록

| | 위험 | 대비 |
|---|---|---|
| 1 | **pointnet2가 Python 3.12에서 안 빌드된다** | S0에서 제일 먼저 확인. 실패 시 `sam6d`를 Jazzy + Python 3.11로 시도 |
| 2 | 새 torch/ultralytics 조합에서 **결과 숫자가 미세하게 달라진다** | S2의 오프라인 대비 비교로 잡는다. 차이가 크면 humble 환경 버전에 맞춰 고정 |
| 3 | **한 장 처리 시간이 너무 길다** (설정에 물체 항목이 15개라 ISM이 무겁다) | S1에서 측정. 초과 시 ① 세션별 물체 줄이기 ② high/low 템플릿 통합 ③ ISM 한 번에 처리 ④ 재생 속도 낮추기 |
| 4 | bag의 시각이 **촬영 시각이 아닐 수 있다** | 변환본(`convert.py --time-source color_global`)만 입력으로 허용하고 `run_meta.json`에 기록 |
| 5 | 나중에 SLAM bag과 SAM bag을 **동시에** 틀면 토픽 이름이 완전히 같아 충돌한다 | 재생할 때 이름 바꾸기(`--remap`)로 카메라 A/B 분리, `--clock`은 한쪽만 |
| 6 | 기존 humble 환경을 **망가뜨리는 것** | `sam6d`는 **새 환경**이고 기존 `sam6d_ros_humble`/`sam_yolo`는 손대지 않는다. 오프라인 경로는 계속 그대로 동작 |

## 9. 이번 범위가 아닌 것

- 인식 정확도 개선 — 이번 목표는 **오프라인과 같은 결과를 실시간으로 내는 것**이다.
- 진짜 카메라 연결 — 지금은 bag 재생이 입력이다. 토픽 이름이 같아서 나중에 카메라로 바꿔도 코드 변경은 없다.
- GUI / Unity / 노트북 2대 운용.
