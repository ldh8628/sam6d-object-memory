## 1. ① "우유인데 0.64" — 전제가 틀렸다

### 1.1 스코어의 정체

코드 실측(`yolo_ism.py:324` `masked_appe_score`, `:238` `semantic_score`):

```python
# appe: 쿼리 전경 패치마다 템플릿 패치와의 최대 코사인 → 평균
sim = query_fg @ template_patches.T
return float(sim.max(dim=1).values.mean().clamp(0, 1))
```

- **확률/신뢰도가 아니라 DINOv2 임베딩의 코사인 유사도 평균**이다.
- softmax도, 배경/음성 클래스 대비 정규화도 없다. 즉 **0.64 = "64% 확신"이 아니다.**
- 비교 대상은 **실사진 vs CAD 렌더 템플릿**이라 도메인 갭이 상수로 깔린다.

### 1.2 그래서 0.64가 어디쯤인가 (milk, 실측)

같은 우유 템플릿 뱅크에 대해 4개 모집단을 측정:

| 모집단 | appe 중앙값 | 의미 |
|---|---|---|
| 랜덤 배경 박스 (n=120) | **0.383** | 우연 수준 바닥 |
| 우유로 **오검출**된 것 (n=11) | **0.558** (max 0.568) | 틀린 판단 |
| **진짜 우유** (n=114) | **0.656** (mean 0.643, max 0.760) | ← 사용자가 본 0.64 |
| 우유 템플릿 vs 자기 형제 템플릿 (n=11) | **0.661** (max 0.801) | 렌더끼리, 블러·가림 없음 |

**핵심:** 도메인 갭도 블러도 가림도 없는 **동일 객체 렌더끼리도 0.661**이다. 실제 우유가 0.656이면 사실상 **도달 가능한 상단에 붙어 있다.** 0.64는 낮은 게 아니라 이 지표의 정상 동작점이다.

실효 구간은 `[0, 1]`이 아니라 대략 **`[0.55, 0.80]`** 이고, "틀림 0.558 → 맞음 0.656"의 **폭이 0.1밖에 안 되는 압축된 스케일**이다. 사람 눈에 0.64가 낮아 보이는 건 스케일 탓이지 인식 실패가 아니다.

> 확인 프레임: `frame_000318.png` — 화면 가득한 명백한 우유가 `sem=0.554 appe=0.646 pem=0.603`. 라벨 = 정답(TP).

### 1.4 ①-b "강체인데 왜 0.8~0.9가 안 나오나" (프레임 38~47) — 사용자 직관이 맞다

프레임 38~47은 Sauce(오렌지 병, 강체)·choco(박스, 강체)·Dinosaur가 근접·선명하게 잡히는데 sem 0.4~0.6, appe 0.6~0.7이다. "강체면 0.8~0.9여야 하지 않나"는 **정당한 의문이고, 실측으로 그렇다는 게 확인됐다.**

같은 객체를 **세 가지 매칭 방식**으로, 동일한 마스킹·동일한 코드로 측정 (`domaingap_masked.py`, 객체당 실물 TP crop 40장):

| 객체 | R→CAD **(현재 프로덕션)** | R→R (실물 vs 실물) | 도메인 갭 |
|---|---:|---:|---:|
| milk | **0.658** | **0.917** | +0.26 |
| saffron | **0.776** | **0.899** | +0.12 |
| Sauce_high | **0.677** | **0.874** | +0.20 |
| Sikhye_high | **0.681** | **0.858** | +0.18 |
| choco | **0.636** | **0.865** | +0.23 |

- **R→CAD 열이 `scores.csv`와 소수점 셋째 자리까지 일치**(0.677=0.677, 0.636=0.636 …) → 프로브가 프로덕션과 동일함이 검증됨.
- **R→R = 같은 강체를 다른 실물 사진끼리 비교하면 0.86~0.92** → 사용자가 기대한 0.8~0.9 밴드에 정확히 들어온다. 객체가 애매해서도, 검출이 나빠서도 아니다.
- 추가로 CAD→CAD(렌더끼리) = 0.78~0.87로 **높다.** 즉 렌더는 렌더끼리, 실물은 실물끼리 잘 맞는데 **실물↔렌더만 못 맞는다** = 전형적 sim-to-real 도메인 갭.

**결론:** appe/sem이 0.6~0.7에 머무는 건 **템플릿이 CAD 렌더라서**다. DINOv2가 실사진과 합성 렌더의 텍스처·조명·센서노이즈를 다르게 임베딩하기 때문이고, 이건 **threshold로도 검출기 개선으로도 못 고친다 — 도메인 갭을 좁혀야 한다.** (그림: `output_slam/ism/SAM_105314_domain_gap.png`)

> 이것이 §1.2의 "천장 0.66"의 진짜 정체다. 천장이 낮은 게 아니라, **실물↔렌더 천장이 0.66이고 실물↔실물 천장은 0.9다.** 우유는 후자 기준이면 0.92까지 나온다.

### 1.3 진짜 문제는 따로 있다 — 객체 간 비교 불가

각 객체의 **틀린** 검출 appe 중앙값을, 우유의 **맞는** 검출(0.656)과 비교:

| 객체 | FP appe 중앙값 | |
|---|---|---|
| **Bear** | **0.676** | ← 틀린 판단이 맞는 우유보다 높음 |
| **Dinosaur** | **0.668** | ← 틀린 판단이 맞는 우유보다 높음 |
| Mugcup_high | 0.573 | |
| Febreze_high | 0.568 | |
| choco_hazelnut_high | 0.568 | |
| saffron | 0.561 | |
| milk | 0.558 | |

appe는 **"그 객체 자기 템플릿과의 유사도"**라 스케일이 객체마다 다르다. 그런데 게이트는 전역 0.55 단일값이다. **이게 config에 기록된 per-object threshold 삽질이 세 번 반복된 근본 원인이다.**

### 3.2 사용자 기준("차이가 크지 않으면 잘못된 것") 적용

**통과 — 강체 상품 5종.** 예: 우유는 TP 중앙값 0.656 vs FP 0.558로 **+0.098** 벌어지고 AUC 0.985. FP 최댓값(0.568)이 TP 25분위(0.636)보다 **낮다**. 스코어는 제 일을 하고 있다.

**실패 — 봉제인형 2종.**

| | TP 중앙값 | FP 중앙값 | 차이 |
|---|---:|---:|---:|
| **Bear** appe | 0.683 | 0.681 | **+0.002** |
| **Dinosaur** appe | 0.655 | 0.668 | **−0.013** |

Bear는 곰과 흰토끼의 appe가 **소수점 셋째 자리에서 갈린다**. Dinosaur는 **음수** — 진짜 초록 공룡이 흰토끼보다 낮게 나오는 일이 더 잦다(AUC 0.427 = 우연보다 나쁨).

> 이 수치는 config에 기록된 기존 관측("block 11은 진짜 공룡을 흰토끼보다 낮게 랭크, AUC 0.47 = 우연 이하")을 **다른 데이터셋에서 독립적으로 재현**한 것이다.

원인은 DINOv2의 shape bias다. 곰·토끼·공룡은 전부 "둥글고 무광인 덩어리"라 형태 신호가 동일하다. **색이 유일한 판별 신호인데 최종 블록(11)은 색을 거의 안 들고 있다.**

## 4. 종합 판정

1. **"우유 0.64"는 버그가 아니다.** 지표를 확률로 읽은 오해다. 0.64는 우유의 정상 동작점이고 오검출(0.558)과 명확히 분리된다.
2. **다만 지적 자체는 절반 옳다.** 스케일이 `[0.55, 0.80]`으로 압축돼 있고 **객체마다 스케일이 달라** 사람이 읽을 수 없다. 전역 게이트 0.55는 원리적으로 정당화 불가다.
3. **사용자 기준의 "잘못된 스코어"는 봉제인형에만 해당한다.** Bear(+0.002), Dinosaur(−0.013)는 스코어가 맞고 틀림을 전혀 못 가른다. 강체 상품 5종은 AUC 0.90~0.99로 멀쩡하다.
4. **choco의 43% FP는 스코어가 아니라 게이트 위치 문제다.** 재조정으로 91% 제거 가능하다.
5. **강체 점수가 0.6~0.7에 갇힌 근본 원인은 CAD 렌더 템플릿(도메인 갭)이다.** 실물끼리면 0.86~0.92가 나온다(§1.4). 절대 점수를 올리려면 threshold가 아니라 템플릿을 실사진 기반으로 바꾸거나 렌더 포토리얼리즘을 높여야 한다.

## 5. 다음 액션 제안

**A. appe 게이트 객체별 재조정 (강체 5종만, 인형 제외)**
`milk 0.573 / Mugcup 0.590 / choco 0.597 / saffron 0.590`. 이 데이터셋 기준 TP 5% 손실로 FP 89~100% 제거. 다만 config에 "per-object threshold는 이미 세 번 되돌려졌다"는 경고가 있으므로, **다른 데이터셋(110104/110633 등) 교차검증을 붙여야** 또 되돌리지 않는다.

**B. 인형은 appe_blocks에 색을 넣어야 함 (별도 트랙)**
Bear/Dinosaur는 게이트로 못 고친다(FP 제거 0%). config의 `[2, 9]` 스윕이 이미 "block 2 = 색"이 인형에 결정적임을 보였고(Dinosaur block2 AUC 1.00 vs block11 0.47), 내 측정도 block 11의 실패를 재확인했다. 단 `[2,9]`는 **게이트 재캘리브레이션 없이는 순 손해**라는 것도 config에 기록돼 있다.

**C. NMS 손실 27건 회수**
게이트 통과분의 15%가 NMS에서 증발한다. `--nms-rank appe`는 이미 기본값이므로, 남은 손실은 IoU 0.5 임계나 단일슬롯 정책 쪽을 봐야 한다.

**D. 스코어 리포팅 UX**
객체별 z-score나 "FP 밴드 대비 마진"으로 바꿔 표시하면 "0.64가 낮다"는 오해가 구조적으로 사라진다.

**E. 도메인 갭 축소 — 절대 점수를 올리는 유일한 길 (§1.4)**
현재 강체 점수 0.6~0.7의 원인은 CAD 렌더 템플릿이다. 세 갈래: (1) **실사진 기반 온보딩** — 실제 장면에서 객체 crop을 몇 장 떠서 템플릿 뱅크에 섞으면 R→R 경로가 열려 점수가 0.85+로 올라간다(가장 직접적, 하지만 뷰 커버리지 필요). (2) 렌더 포토리얼리즘 향상(조명·재질). (3) 도메인 적응 특징. **주의: 점수를 올리는 것 자체가 목표는 아니다** — 분리도(§3)가 이미 강체는 좋으므로, E는 "점수가 낮아 불안하다"는 UX/신뢰 문제와 인형처럼 갭이 큰 케이스에 의미가 있다.
