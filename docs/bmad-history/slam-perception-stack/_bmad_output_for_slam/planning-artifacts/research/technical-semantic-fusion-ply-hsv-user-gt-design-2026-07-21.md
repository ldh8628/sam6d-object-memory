## 1. Semantic score 통합 방식 재검증

### 1.1 방법론 — 왜 임베딩을 덤프했는가

aggregation 변형을 바꿀 때마다 모델을 재실행하면 변형 1개당 수십 분이 든다.
대신 **박스별 DINOv2 CLS(384차원)를 한 번만 저장**했다. 42-view 유사도는
`TCLS[object] @ cls[uid]` 한 번의 행렬곱이므로 이후 모든 변형이 오프라인 즉시 계산된다.

- 대상: 6개 데이터 전 후보 박스 **22,436개** → 39.1 MB, 소요 **22초**
- 후보 pair(박스×객체) **28,894**, 유사도 복원 실패 **0**
- **재현 검증**: 복원한 top-5 와 이전 덤프의 `sem_top5` 차이가 최대 **0.00005** (덤프가 소수 4자리 반올림) → 복원이 정확함을 확인

### 1.2 비교한 공통 방식

객체별로 다른 규칙을 쓰는 안은 지시대로 제외했다. 후보는 전부 **전 객체 동일 규칙**이다.

| 계열 | 방식 |
|---|---|
| Top-k 평균 | `top1`, `top3`, `top5`(현행), `top10`, `top20`, `top42`(=전체 평균) |
| 하위/일관성 | `min1`(최저 1개), `bottom5`(최하위 5개 평균), `mean_minus_std`, `trim0_5` |
| 비산술 평균 | `harmonic`, `geometric` |
| 결합 | `fusion_α` = α·z(S_top5) + (1−α)·z(S_mean), α = 0.00 ~ 1.00 (0.05 간격, 21개) |

`z(·)` 는 표준화이며, **평균·표준편차는 calibration fold 의 전 후보 pair 에서만** 추정했다
(라벨이 필요 없는 통계라 라벨된 부분집합에 한정할 이유가 없다).

### 1.3 평가 설계 — 순위 지표와 결정 단위를 모두 본다

운영 판정은 *"후보 박스 중 semantic 최대인 것을 고르고 두 게이트를 통과시키는"* 구조라,
점수를 바꾸면 **선택 자체가 바뀐다.** AUROC 만으로는 이 효과가 보이지 않는다.

```
결정 단위 정의 (라벨이 완비된 (frame, object) 그룹만 — 분모 고정)
  TP : 수락했고, 선택된 박스의 true_class == 대상 객체
  FP : 수락했으나, 선택된 박스의 true_class != 대상 객체
  FN : 수락하지 않았으나, 그룹 안에 true_class == 대상 객체인 박스가 존재
  TN : 수락하지 않았고, 그룹 안에 해당 객체가 없음
```

- 후보 그룹 16,549 중 **라벨 완비 그룹 347** (박스 380)
- **threshold 는 calibration fold 에서 F1 최대로 결정하고, held-out fold 에서만 채점**했다.
  기존 `similarity_threshold=0.35` 를 새 점수에 그대로 쓰면 스케일이 달라 비교가 성립하지 않는다.

### 1.7 최종 선택 — 판정과 그 근거

지시하신 최우선 기준은 *"FP와 FN이 모두 악화되지 않을 것"* 이다. 이를 **엄격히** 적용하면:

> **어떤 방식도 이 기준을 만족하지 못한다.** ΔFP < 0 인 모든 방식은 ΔFN ≥ +1 이다.
> 이 기준만 보면 답은 **A (Top-5 유지)** 가 된다.

그러나 그 판정을 가르는 것이 **347 그룹 중 단 1건**이므로, 그 1건을 직접 확인했다.

```
fusion α=0.25 가 Top-5 대비 바꾼 그룹 9건
  FP → TN  8건 (오류 제거)
  TP → FN  1건 (신규 오류)  ← sam_110104 f410, Dinosaur, 선택 박스 변경 없음
```

신규 FN 1건은 **선택이 바뀐 것이 아니라 점수가 임계 바로 아래로 내려간 경계 사례**다.
반면 제거된 FP 8건의 정체는 다음과 같다.

| 데이터셋 | 프레임 | 대상 객체 | 실제 정체 |
|---|---:|---|---|
| sam_105018 | 125 | choco_hazelnut_high | **carton (갈색 택배박스)** |
| sam_105018 | 310 | choco_hazelnut_high | carton |
| sam_105314 | 345 | choco_hazelnut_high | carton |

**이전 조사에서 확정한 두 최대 실패 모드(초코↔갈색 택배박스, 인형 상호혼동)를 정확히
겨냥해 제거한다.** 신규 FN 은 통계적으로 0 과 구분되지 않는다(95% CI [0, +3]).

따라서 판정은 **C. Top-5 + 전체 평균 공통 결합** 이며, 권장값은 **α = 0.30** 이다.
다만 이 판정은 "FN +1 을 잡음으로 볼 것인가" 라는 해석에 의존하므로, 표본을 늘려
재확인하는 것을 §5 의 선결 조건으로 둔다.

```
선택: C. Top-5 + 전체 평균 공통 결합
      S_fusion = 0.30 · z(S_top5) + 0.70 · z(S_mean)
      (α 0.25~0.45 구간에서 결과 동일 — 정밀 튜닝 불필요)
```

### 1.8 왜 객체마다 방향이 다른가 — 원인 재확인

직전 보고서에서 확정한 기전이 이번 데이터에서도 재현된다:
**`sem_mean` 의 우열은 오직 "꼬리(6~42위 view)가 상위 5개보다 변별력이 높은가" 로 결정된다**
(상관 +1.000, n=10).

높은 변별력을 보존하고, 개선형 객체는 mean 성분이 꼬리의 신호를 끌어온다.
평균 AUROC 가 top5(0.8913)와 mean(0.9360) 어느 쪽보다도 높은 **0.9386** 이 되는 것이 그 증거다.

### 1.9 이 결과의 한계 (반드시 함께 읽을 것)

- **라벨 완비 그룹이 347개**로 작다. FN 이 11~14 건 규모라 ±2~3 건의 변동이 결론을 흔든다.
- **라벨 504건 전부가 Claude Vision 잠정 라벨**이며 사람 검수 0건이다(대기열 79건 미처리).
- 신규 FN 3건이 **전부 Dinosaur** 라는 점은 **객체 간 점수 스케일 차이** 때문일 수 있다.
  단일 전역 threshold 를 쓰면 한 객체의 FP 를 다른 객체의 FN 과 교환하게 된다.
  (config 에는 객체별 `similarity_threshold` 구조가 이미 있으나 현재 전부 0.35 로 동일하다.)
  이는 **aggregation 방식과 독립된 별개 사안**이므로 이번 결론을 바꾸지는 않는다.

## 2. PLY 기반 HSV 방식 정밀 검증

### 2.1 먼저, HSV 가 무엇인가

색을 세 축으로 나눠 보는 방식이다.

```
Hue (색상)        = 빨강, 노랑, 초록, 파랑처럼 "색의 종류"
                    OpenCV 에서는 0~179 로 저장되며, 실제 각도(0~360°)의 절반이다.
Saturation (채도) = 색이 얼마나 선명한가. 0 이면 회색, 높으면 쨍한 색.
Value (명도)      = 밝기.
```

조명이 바뀌면 **Value 가 가장 많이 흔들리고 Hue 가 가장 덜 흔들린다.** 그래서 색으로
물체를 구분할 때는 보통 Hue 와 Saturation 을 쓰고 Value 는 빼거나 약하게 쓴다.
이번 실험도 **H(16 bin) × S(8 bin) 결합 히스토그램**을 기본으로 썼다.

### 2.7 저채도 객체에서 Hue 가 불안정한 이유

**Rabbit 의 평균 채도는 2.4 (0~255)** 다. 사실상 흰색/회색이다.

HSV 변환에서 Hue 는 R, G, B 중 최대·최소의 **차이로 나누어** 계산된다.
채도가 0 에 가까우면 그 분모가 0 에 가까워져, 센서 잡음 수준의 미세한 RGB 차이가
Hue 를 0°~360° 어디로든 튀게 만든다. 즉 **무채색 물체의 Hue 는 값이 아니라 잡음**이다.

실측이 이를 뒷받침한다.

- Rabbit: 현행 0.9340 → 공통 Hue 보정 **0.8905 (악화)** → 저채도 예외 적용 **0.9309 (회복)**
- 반면 채도가 높은 Bear(76.8)·Sauce(74.8)·Sikhye(147.6)는 보정으로 크게 개선

따라서 **평균 채도 임계(이번 실험에서는 20/255)를 두고 그 아래 객체는 Hue 보정에서 제외**해야
한다. 이 예외 하나로 평균이 0.9569 → **0.9590**, 최저 객체가 0.8908 로 유지된다.

### 2.8 Hue `−5.6°` (이번 실험 −6°) 보정은 어떤 변환인가

```
보정 전 픽셀:  (H, S, V)
보정 후 픽셀:  ((H − 6°) mod 360°, S × 1.3, V)     ← 원형 회전 + 채도 이득
```

- **원형 회전인 이유**: Hue 는 색상환(0°와 360°가 같은 빨강)이므로 단순 뺄셈이 아니라
  **순환 이동**이어야 한다. 코드에서는 OpenCV 단위(0~179)에서 `(h - 3) % 180` 이 된다.
- **왜 음수인가**: 렌더가 실사보다 Hue 를 **오른쪽(값이 큰 쪽)으로 밀고 있기** 때문이다.
  Bear 렌더 peak 13 vs 실사 7, saffron 22 vs 12, Sikhye 23 vs 17.
- **왜 필요한가**: blenderproc/Blender 3.3.1 의 POINT 광원 셰이딩·색공간 처리가
  vertex color 를 그대로 재현하지 않기 때문이다. §2.4 의 채도 −26~38% 와 같은 원인이다.
- **채도 ×1.3 의 근거**: 렌더/PLY 채도 비가 Bear 1.40, Dinosaur 1.37, choco 1.40,
  saffron 1.53 로 1.3~1.5 대에 몰려 있고, LODO 가 독립적으로 1.3 을 골랐다.

### 2.10 FP/FN 변화 가능성

이번 HSV 실험은 **박스 단위 순위 지표(AUROC/PR-AUC)** 까지만 측정했고,
**결정 단위 TP/FP/FN 은 측정하지 않았다.** HSV 를 최종 점수에 넣으려면
게이트 구조와 임계를 새로 설계해야 하는데, 그것은 이번 지시 범위 밖이다.

정량적으로 말할 수 있는 것은 PR-AUC 변화뿐이다: **0.5478 → 0.7705 (+0.223)**.
PR-AUC 는 불균형 데이터에서 precision-recall 상충을 요약하므로,
**FP 를 줄일 여지가 크다는 신호**로 읽을 수 있으나 **FP/FN 건수 예측은 아니다.**

### 2.11 공통 보정값이 다른 조명에서도 유효한가

**현재 산출물로는 확인할 수 없다.**

6개 데이터가 **모두 같은 날, 같은 사무실**에서 촬영됐다. LODO 는 *데이터셋 간* 누수를
막지만 *조명 조건 간* 일반화는 검증하지 못한다. 이번에 확인한 "6/6 fold 에서 동일한
보정값 선택"은 **같은 조명 안에서의 안정성**이며, 다른 조명에서도 −6°/×1.3 이 최적이라는
근거는 없다.

또 하나 짚어야 할 점: **보정각 자체가 실사 crop 에 맞춰 추정된 값**이다.
prototype 은 여전히 렌더만 쓰므로 "실사 prototype 을 운영 자산으로 쓰지 않는다"는
지시는 지켰지만, **스칼라 2개(−6°, ×1.3)는 이 사무실 데이터에 적합된 값**이다.
실사 히스토그램 N개를 자산으로 갖는 것보다 훨씬 가벼운 약속이지만 **0 은 아니다.**

**5. semantic + appearance + HSV 결합 실험에 사용할 HSV 방식은 무엇인가?**

```

      · Hue  : -6°  (원형 이동)
      · 채도 : x1.3
```

- 객체별 **visible positive frame** 수 (지금까지 존재하지 않던 분모)

- **proposal miss** — 단계 분해 가능: raw 부재 / conf·NMS 제거 / 객체별 threshold / top_k 절단

- `S` 층을 이용한 **객체 크기·가림 수준별 recall**

```text
확정되었다.

채택할 HSV 생성 방식:
- 렌더 42-view (PLY 전체도 PLY 42-view 도 채택하지 않음)
  · 전 객체 공통 색보정: Hue -6° 원형 이동 + 채도 x1.3
  · 예외: 평균 채도 < 20/255 인 객체는 Hue 보정 미적용 (현재 Rabbit 하나)
  · 특징: masked H(16) x S(8) 히스토그램, Bhattacharyya 유사도, 42개 중 max
  · LODO held-out 평균 AUROC 0.8473(현행) → 0.9590, PR-AUC 0.5478 → 0.7705,
    최저 객체 0.5192 → 0.8908
- PLY 를 채택하지 않는 이유: 방식 A(전체 1개) 0.8581, 방식 B(시점별 42개) 0.8630 으로
  둘의 차이가 +0.005 에 불과하고, 보정된 렌더(0.9590)에 크게 못 미친다.
  시점 변동도 렌더와 비슷해 "시점별이 더 안정적" 이라는 근거가 없으며,
  milk 는 정점이 16,302개뿐이라 최근접 거리가 30.5 mm 로 방식 B 자체가 성립하지 않는다.
  다만 PLY 는 진단 도구로서 결정적이었다 — 렌더 대비 채도가 26~38% 높다는 사실이
  "렌더러가 색을 왜곡한다" 는 원인 규명과 채도 gain 1.3 의 근거를 제공했다.

Hue 의 의미와 보정 방식:
Hue 는 빨강·노랑·초록·파랑처럼 "색의 종류" 를 나타내는 값이고(OpenCV 는 0~179 로 저장하며
실제 각도의 절반이다), Saturation 은 색의 선명한 정도, Value 는 밝기다.
보정은 (H, S, V) → ((H - 6°) mod 360°, S x 1.3, V) 이며, Hue 는 색상환이므로 단순 뺄셈이 아니라
순환 이동이어야 한다. 음수 방향인 이유는 렌더가 실사보다 Hue 를 오른쪽으로 밀기 때문으로,
Bear 렌더 peak 13 vs 실사 7, saffron 22 vs 12, Sikhye 23 vs 17 에서 확인된다.
보정값은 LODO 학습 fold 에서만 추정했고 Hue 단독은 6 fold 중 5 fold 가 -10°,
Hue+채도는 6 fold 중 4 fold 가 (-6°, x1.3) 로 안정적으로 선택됐다.
저채도 객체에서 Hue 가 불안정한 이유는 HSV 변환에서 Hue 가 RGB 최대·최소의 차이로 나누어
계산되기 때문이다. 채도가 0 에 가까우면 분모가 0 에 가까워져 센서 잡음이 Hue 를 어디로든
튀게 만든다. Rabbit 의 평균 채도는 2.4/255 로 사실상 무채색이며, 실제로 공통 보정을 걸면
0.9340 → 0.8905 로 악화하고 예외 처리하면 0.9309 로 회복한다.
공통 보정값이 다른 조명에서도 유효한지는 현재 산출물로는 확인할 수 없다 —
6개 데이터가 모두 같은 날 같은 사무실이라 LODO 로는 조명 일반화를 검증할 수 없다.

실사 prototype 사용 여부:
사용하지 않음. prototype 은 렌더 템플릿만 쓴다. 기존 6개 데이터의 실사 crop 은 평가 기준으로만
```
